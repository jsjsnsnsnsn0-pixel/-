# CP and global gift updates

Existing love / soulmate behavior stays available through `couple_action`, `couple_state`, `profile_cp` and existing weekly rewards. The migration assigns existing rows to `love`; it never ends an existing relationship. It aborts if legacy data contradicts exclusivity.

`cp_types` contains only the current enabled `love` type. Future types are added by a trusted database administrator after product rules are agreed. The typed endpoints are `cp_action(p_public_id, p_action, p_type_id)` and `cp_state()`. Ordinary accounts cannot edit types or conflict rules.

Accepted relationships claim two `private.cp_slots` records. Their `(user_id, type_id)` primary key prevents the same type being accepted with another person regardless of canonical pair ordering. A partial unique pair index also prevents two accepted types between the same pair. Participants are locked in UUID order before mutation, and triggers validate requests and acceptances as well as managing slots. Ending releases only that relationship's slots. Same-type and conflicting pending requests are cancelled on acceptance; compatible types with other partners remain available. The optional `private.cp_type_conflicts` table defines additional conflicts between types for a participant; its type keys must be sorted. Existing love rankings and rewards remain love-only.

Global gift eligibility is explicitly configured through the server-only `gift_catalog.global_announcement_enabled` flag, default false for every gift. No amount threshold is assumed. Once agreed, trusted administration can flag individual gifts. Successful server gift accounting inserts a room feed record and creates one global announcement per feed ID. Retries cannot create another announcement. Both ordinary and self gifts use the same feed trigger; their accounting and deferred self-gift reward rules stay unchanged.

Private rooms never emit global announcements. The read policy excludes unavailable rooms, banned users, and VIP rooms the viewer cannot enter. It exposes only gift identifiers/names, public display names and a room identifier, with a 20-second expiry. Authenticated clients can only read. The global UI subscribes to database changes, catches up through short bounded polling, discards stale events, deduplicates, queues at most three, and shows each for at most 4.2 seconds. It reserves a compact top lane, honors reduced motion, offers dismissal, and navigates using the existing room list and atomic server join. Failed entry preserves the previous room membership.

Validation: frontend type/lint/assets/build and unit/DOM tests; transactional database tests in `tests/database-cp-global-gifts.sql` plus existing commerce, room and gift accounting regressions. Fixtures are rolled back. Managed browser QA was unavailable in this environment, so visual review remains through the private preview.

Avatar asset: `public/assets/images/ruby_wings_transparent.png`, generated using the built-in image tool from the original JPEG; true RGBA transparency was verified at the corners and circular center. ## Follow-up: global avatar header and authoritative CP reads

The preview's former profile fixture mapped every non-Laila account to Laila, falsely showing a second CP partner. It now models exactly one reciprocal example pair (Dawlat Al-Iraq and Laila); Ahmed has no active CP. Conflicting example requests are rejected. Preview root and `/review.html` now build the same current UI, with clean output removing obsolete chunks.

Every room profile card uses `ProfileAvatarHeader`, with the same transparent RGBA frame for every account. The frame lives at `src/assets/profile-ruby-wings.png`; Vite generates a content-hashed asset URL. Header containers are explicitly transparent. Broken frame loading hides only the decorative frame; it never falls back to an opaque JPEG. Profile and avatar behavior stays unchanged.

The profile loader no longer consults viewer-scoped `couple_state` as a fallback. `profile_cp` is the only CP source for popup presentation. Null, failure, wrong target/type, ended, malformed and self-linked results clear the optional CP section. The backend now returns target/relationship/type/acceptance metadata and validates both exclusivity slots and canonical accepted records. `profile_cp_by_type` supports future types without changing the current default love endpoint. Contradictory or incomplete old records are excluded from public profile reads, and canonical accepted rows still block new conflicting requests even if occupancy is malformed. An audit found no invalid active records in the existing database, so no user relationships were deleted.

Open room cards revalidate on relationship events, focus and a 15-second polling fallback (needed when a third-party viewer cannot receive private relationship changes). Detail profiles also revalidate and never display an accepted relationship that disagrees with the canonical public read. Transactional fixtures verify reciprocal reads, pending/ended exclusion, malformed slots, conflict rejection and replacement of a terminated partner. Frontend tests cover all three example user roles and stale fallback rejection.
